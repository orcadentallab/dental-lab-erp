## Delivered behavior

- `/design-qc` is available to admin, coordinator, assigned designers and eligible secondary designers. Production workspace navigation groups existing authorized destinations; it grants no new backend production mutation rights. Settings links to the switch.
- First new submission/file change after activation requires review. Historical designs already beyond the stage do not acquire fabricated approvals or retrospective gates. Submissions during pause remain exempt when reopened. An older pending required revision retains its history and becomes gated again on reopening.
- Execution ZIP up to 50 MiB; standalone HTML up to 10 MiB, or an explicit no-preview reason. Storage-generated eTags identify bytes. Reuploading identical execution/preview bytes keeps the current revision and approval, records the reference/submission event, and supports idempotent RPC retry.
- Admin approves/rejects; rejection needs notes. Admin/coordinator can bypass with a reason. Neither can bypass execution bytes previously rejected, including reuploads with a new URL or UUID. Changed execution files can be reviewed/bypassed as a new revision.
- A later rejection after bypass remains recorded and appears in the coordinator follow-up queue. It does not automatically stop production. Explicit return to the same designer preserves earned fees. Priced reassignment is an admin action; coordinator retains bypass/release/same-designer return. No financial approval queue was added.
- Order status, stage start/finish and external work dispatch guards enforce the gate. Running stages/external dispatch snapshot their execution revision; a later upload does not silently change the files already being executed. Design-stage completion remains outside the execution gate, preserving designer earning timing.
- New file download/copy consumers in OrderCard, DesignerDashboard, MyTasks and ProductionBoard resolve the immutable copy, with a stage snapshot where applicable. Legacy cases without a QC revision retain their existing link path.
- Revision/decision records cannot be rewritten or deleted through authenticated table access. Restrictive Storage policies prevent overwriting/deleting files even for an operational admin. Reads and new signed URLs require current assignment/role; a former designer loses revision/file access while retaining a separate personal financial read.
- Reviewer identity/time/notes and previous versions remain visible to authorized current reviewers/designers. Financial assignment details are not exposed through the shared technical revision history.

## Financial handoff and unchanged rules

`reassign_design_revision` locks the order and records an immutable command ID, former/replacement designer, selected amounts, reason, actor and time. Repeating the same command does not duplicate settlement. The former normal obligation is voided and its allocations move through the existing allocation/credit functions to the explicitly chosen manual settlement. The replacement earns its default/overridden fee at actual design completion, before QC approval. A salaried designer retains existing per-case exclusion.

Worked SQL acceptance: former design fee/payment 100; former final settlement 80; 80 stays allocated and 20 remains an advance/credit for the former designer. The original cash transaction remains 100. Replacement fee 90 is earned only at completion. Designer-specific service override 20 × 2 units defaults to 40; normal service default 15 × 2 defaults to 30 when override is blank.

Former contributions are **independent manual settlements**, traced to the case through `design_qc_assignments`, rather than active liabilities of the current order. `financial_obligations.order_id` may be null only for this specifically linked settlement shape. Ordinary obligation creation still requires an order. The final schema preserves `assert_zero_issue_has_no_active_obligations` without any QC exception; existing Remake/Reject/Return and current-order zero-impact handling are unchanged. No historical obligations were converted. Migration 280 also removes an intermediate local-development guard exception without updating any historical row.

Accounts and Statements append an explicitly labelled financial-only former-contribution projection to their common statement/export data. It contains no doctor account, selling price, supplier, clinical case row or workflow action. It does not feed production lists. Existing statement computations are reused. No revenue/profitability formula, cash source, `approved` meaning or production financial source selection was changed.

**Remaining integration gate:** general case cost/profit reports still use their existing current-order cost inputs. Aggregating separately settled former contributions into the per-case cost reconciliation/report package (13) is not completed here. Do not enable priced handoffs in production before that reconciliation and financial consumer acceptance. The new financial right itself is recorded and readable now.
