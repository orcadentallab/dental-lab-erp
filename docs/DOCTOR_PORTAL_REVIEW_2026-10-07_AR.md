## القرار والتنفيذ الأحدث: الحساب بكلمة مرور، ودعوات المعمل

هذا القسم يستبدل مسار الجهاز والمراجعة لكل الأطباء الوارد في التاريخ أدناه، بناءً على طلب صاحب المشروع بعد مراجعة LabSync.

- **جديد:** بيانات كاملة + كلمة مرور وتأكيدها، إنشاء الطبيب والمركز والفروع والأطباء التابعين بكود المنطقة، ثم دخول فوري.
- **قديم بدعوة:** من بطاقة الطبيب زر «دعوة لتفعيل حساب الطبيب». يعرض رابطًا لنسخه وإرساله يدويًا. الدعوة تخص السجل، 256-bit، بصمتها فقط مخزنة، مدتها 7 أيام، مرة واحدة؛ الدعوة البديلة تلغي السابقة. التسجيل يربط الحساب مباشرة، ويحفظ أرقام التواصل والفروع الإضافية. العنوان الرئيسي يحتاج طلب تعديل معتمد؛ الكود والأسعار والمالية لا تتغير.
- **قديم دون دعوة:** الهاتف يعرض الاسم والعنوان والفروع المسجلة للتعبئة، دون حالات أو أسعار أو أرصدة. الربط يحتاج مراجعة الإدارة/المنسق. الحساب المعلق ممنوع من الحصول على جلسة Auth، وليس مجرد صفحة انتظار تخفي البيانات. الموافقة تفعّل الهوية نفسها وكلمة المرور نفسها.
- **الدخول:** الإيميل أو الموبايل وكلمة المرور من جهاز آخر أيضًا. الموبايل alias غير متحقق منه؛ وظيفة حل alias لا تعرض الإيميل إلا بعد مطابقة كلمة المرور مع hash الحالي، ثم يستخدم العميل تسجيل Supabase بكلمة المرور لإنشاء JWT. لا SMS provider مطلوب. حد المحاولات 10/ساعة للهاتف، وحدود للبحث والتسجيل على الخادم، مع حاجة حماية IP/CAPTCHA على بوابة النشر.
- **كلمات المرور:** bcrypt cost 10، 8 أحرف على الأقل للطبيب وحد 72 بايت، لا كلمات مرور في profiles أو الردود أو التخزين المحلي أو شاشات المراجعة. يتولى Supabase تخزين الجلسة؛ ليست كلمة مرور محفوظة في المتصفح.
- **الاستعادة وإدارة الموظفين:** إدارة المستخدمين تعيد تعيين كلمة مرور الطبيب ولا تقرأ القديمة. إعادة التعيين ترفض المسؤول المعطل. إنشاء Auth للطاقم أصبح admin RPC؛ الهوية تبقى محظورة حتى إدخال public profile وتفعيلها، حتى لا يعطل إغلاق التسجيل العام إضافة الموظفين. الحد الأدنى 8 أحرف للطبيب والطاقم.
- **مسار الجهاز السابق:** وظائف تقديم الطلب وفتح الجلسة ومراجعته أُغلقت أمام anon/authenticated؛ السجلات محفوظة للمراجعة ولا حذف أو تحويل للمالية. الواجهة الافتراضية لا تستعمله. تبقى ملفات التجربة السابقة للتاريخ، ولا ينبغي اعتبارها مسار تشغيل قائم.
- **تفعيل واتساب:** مؤجل كما طلب المالك؛ لاحقًا لإثبات الهاتف واستعادة الحساب دون إنشاء هوية جديدة. بيانات Auth تميز الحساب الحالي بـ`doctor_verification=unverified_password`، والهاتف غير مؤكد؛ كلمة المرور ليست إثبات ملكية الهاتف أو الإيميل.

## تاريخ سابق تم استبداله: تأجيل واتساب وتشغيل تسجيل فعلي بدون OTP

قرار صاحب المشروع الحالي يتقدم على وصف المصادقة المحلي في بقية التقرير: التسجيل بدون كود واتساب، مع اعتماد المعمل قبل إتاحة حساب الطبيب.

- شاشة الدخول الافتراضية تتيح طلب ربط لطبيب قائم أو تسجيل طبيب/مركز وفروعه. الهاتف غير متحقق منه ولا يستخدم كمفتاح دخول.
- الطلبات تحفظ في `doctor_manual_access_requests`، بدون مستخدم Auth أو بيانات حالات قبل الاعتماد. الجدول يمنع القراءة والكتابة المباشرة لجميع عملاء المتصفح.
- المراجع يرى بيانات التسجيل والفروع والأطباء التابعين، ويختار إنشاء حساب جديد أو الربط بسجل موجود بعد التأكد من الهوية. الجديد يستهلك كود المنطقة عند الاعتماد فقط؛ الربط لا يغير الطبيب أو المالية.
- طلب الجهاز يحمل سرًا عشوائيًا 256-bit محفوظًا محليًا، وبصمته فقط على الخادم. جهاز آخر لا يستعيد الحساب بمجرد كتابة الهاتف؛ يحتاج مراجعة جديدة. رفض الطلب وتعطيل المستخدم يمنعان الدخول.
- بعد الاعتماد ينشأ حساب مستقل خاص بالطلب، باستخدام مسار إنشاء `auth.users` و`auth.identities` في SQL، ثم دخول Supabase الاعتيادي بصلاحيات doctor. لا يعيد تعيين كلمة مرور حساب قائم. نقل إنشاء الهوية إلى Supabase Phone Auth الرسمي ضمن تفعيل Meta لاحقًا؛ المسار الحالي مؤقت وليس إثبات ملكية للهاتف.
- فقد بيانات المتصفح/الجهاز يحتاج مراجعة جديدة؛ الأجهزة المشتركة غير مناسبة لحفظ الوصول. تعطيل الوصول من إدارة المستخدمين. OTP المحلي السابق محفوظ عبر `VITE_DOCTOR_ACCESS_MODE=otp`، ولا يفعّل إرسال إنتاج.
- قبل النشر: مراجعة migration وتطبيقها على بيئة الاختبار ثم الإنتاج ضمن إجراء النشر المعتاد، HTTPS، وحماية الطلبات الآلية/حدود IP على بوابة API. توجد حدود SQL (3 طلبات/ساعة للرقم و200/ساعة إجمالًا) وحد إصدار جلسة/10 ثوانٍ لكل طلب، لكنها لا تغني عن حماية الشبكة. لا نشر أو تغيير بيانات مالية في هذه الجلسة.

**تحديث بناءً على توجيه صاحب المشروع:** أزيل تنفيذ توليد الأكواد التلقائي الذي أُضيف دون اعتماد الصيغة. إنشاء الحسابات الجديدة متوقف في الواجهة وRPC إلى حين الاتفاق على سياسة الأكواد. أُوقف اختبار تسجيل المركز المرتبط بهذه الميزة مؤقتًا، وأصبح اختبار SQL يؤكد عدم إنشاء طبيب/كود مع استمرار اختبار عناوين الشحن والفروع. التفاصيل والنتائج السابقة الخاصة بتوليد الأكواد أدناه توثق التنفيذ السابق ولا تعبر عن الحالة الحالية. لم تُعدّل أكواد موجودة، ولم تُحذف حسابات العرض التجريبية.

المرجع: `docs/DOCTOR_PORTAL_MASTER_PLAN_AR.md`، ومراجعة شجرة العمل الحالية، بما فيها الملفات غير المتتبعة. النتيجة: التنفيذ جزئي، وإصلاحات المصادقة والربط قابلة للمراجعة والاختبار محليًا، لكن تسجيل الدخول بالهاتف **غير جاهز للإنتاج** حتى تنفيذ مزود إرسال آمن على الخادم.

لم يتم الاتصال بقاعدة الإنتاج، أو تطبيق ترحيلات عليها، أو تغيير بيانات مالية. جميع بيانات اختبار SQL وحسابات Auth أنشئت في حاويات محلية مؤقتة معزولة. لم يتم إنشاء commit أو نشر التغييرات.

## المشكلات التي أصلحتها

1. **إتاحة رمز mock عبر إجراء مجهول:** أصبح الطلب والتحقق مغلقين افتراضيًا على قاعدة البيانات، ويحتاجان إعداد خادم صريحًا. المتصفح يسمح بالمسار التجريبي في التطوير فقط مع `VITE_OTP_CHANNEL=mock`. يبدأ إصدار الإنتاج بتبويب دخول طاقم العمل.
2. **أسرار Meta داخل المتصفح وإرسال رمز وهمي:** أزلت قراءة `VITE_META_WHATSAPP_TOKEN` وطلب Meta المباشر. لم يعد هناك رمز بديل ثابت `123456` أو ادعاء نجاح إرسال حقيقي. `MetaCloudOtpSender` يعيد عدم تهيئة مزود الخادم بوضوح؛ هذه نقطة إكمال مطلوبة وليست إرسالًا جاهزًا.
3. **NULL OTP واحتمال التحقق المتزامن:** تحقق صارم من ستة أرقام، أقفال للهاتف والسجل، ومنع إعادة استخدام الرمز. التخزين أصبح HMAC-SHA256 بمفتاح خادم بدل bcrypt للرمز، والتوليد يستخدم `gen_random_bytes`. كلمات مرور Auth المؤقتة تبقى bcrypt.
4. **طلبات أكثر من الحد المخطط:** أصبح حد الهاتف ثلاثة طلبات في الساعة مع تسلسل الطلبات المتزامنة. حد IP لا يزال يحتاج نقطة استقبال خادم تستخرج IP موثوقًا؛ لا يكفي `p_ip` الذي يرسله العميل.
5. **طلب ربط يمكن إرساله بمجرد معرفة هاتف تحقق منه شخص آخر:** إضافة `claim_token` عشوائي يصدر لصاحب التحقق عند `not_found`، وتخزين بصمته فقط، وربطه بالهاتف واستهلاكه مرة واحدة خلال ثلاثين دقيقة. توقيع الإجراء الآن `claim_doctor_code(text,text,text)`؛ حُذف التوقيع القديم غير الآمن.
6. **واجهة `not_found` لا تفتح مسار المطالبة الناجح:** إصلاح انتقال شاشة الدخول إلى طلب الكود عند الاستجابة الناجحة لهذا المسار، ومسح أرقام OTP عند إصدار رمز جديد.
7. **اعتماد رقم جديد لا يتيح الدخول لاحقًا:** قرار الاعتماد يمثل خريطة هاتف إلى الطبيب، ويقرأه التحقق التالي قبل مطابقة دليل الأطباء، حتى للرقم الجديد أو المركز. الاعتماد لا يغير هاتف الدليل ولا يعيد تنشيط مستخدم موقوف؛ إنشاء بيانات الدخول يحدث بعد رمز تحقق جديد.
8. **تعارض الحسابات وإعادة توجيهها:** إزالة `ON CONFLICT(username) DO UPDATE` الذي كان قد يستبدل هوية حساب موجود، وحماية تبني Auth identity المرتبطة بمستخدم آخر، ورفض الملفات المتعارضة. استخدام البريد الفعلي للحساب الموجود بدل افتراض البريد الصناعي.
9. **تكامل حساب Supabase:** إضافة سجل `auth.identities` للبريد وتعبئة حقول token اللازمة عند إنشاء الحساب. تم اختبار إصدار جلسة فعلية بواسطة Auth المحلي.
10. **فحص دور NULL ومسار كتابة مباشر:** رفض دور NULL في إجراءات الإدارة، وسحب UPDATE المباشر على طلبات الربط من authenticated؛ المعالجة عبر إجراءات الاعتماد والرفض فقط. أقفال تمنع معالجة الطلب مرتين أو اعتماد الهاتف بالتوازي لحسابين.
11. **اختيار أول طبيب تلقائيًا عند تعدد المطابقات:** لا تختار الشاشة أول سجل في حالة الغموض، وتمنع تنفيذ إجراءات متعددة متزامنة من الواجهة. أصلحت تبعيات hooks في الملفات المرتبطة.
12. **تطبيع متساهل:** إزالة قبول أي رقم من 10–15 رقمًا كرقم دولي؛ الأرقام المحلية المشوهة والبادئات غير المدعومة تعاد كغير صالحة.
13. **جاهزة تعني خرجت للشحن في الواجهة:** `final_ready` يعرض الآن «جاهزة للتسليم»؛ لا يُعرض خروج فعلي دون بيانات شحن. أزلت وعد إخطار فريق الشحن من نجاح طلب الاستلام، وأعدت مدة الطلب الافتراضية إلى الثلاثة أيام السابقة حتى ربط ETA الحقيقي.
14. **الاختبار الجديد غير مشمول بالتحقق المعتاد:** أضفت ملف SQL الخاص بالهاتف إلى `npm run test:db` ووسعت اختبارات الخدمة وقاعدة البيانات.

## أولويات الإكمال

### تحديث بعد ملاحظات تجربة localhost

أُضيف مسار صريح في الدخول يسأل هل سبق التعامل مع المعمل. الطبيب الجديد يتحقق من الهاتف ثم يسجل الاسم والعنوان، ويحدد هل هو مركز، ويسجل أسماء وأرقام الأطباء التابعين الاختيارية والفروع بعناوينها. `register_verified_doctor` يستهلك إثبات الهاتف مرة واحدة، ويمنع إنشاء سجل جديد إذا أصبح الهاتف مرتبطًا بسجل/طلب سابق. توليد الأكواد يتم عبر sequence على الخادم، ثم يُنشأ حساب doctor مرتبط بالسجل الجديد. المراكز الجديدة تستخدم خريطة الربط المعتمدة عند الدخول اللاحق.

هذه الميزة، مثل OTP السابق، مفعلة محليًا فقط؛ لا تعني تشغيل تسجيل الهاتف على الإنتاج دون نقطة إرسال وتحقق آمنة على الخادم.

أصبح نموذج الطلب يعرض عنوان الطبيب مباشرة وخيار العيادة الرئيسية والفروع المسجلة. اختيار الفرع يملأ عنوانه ويمكن تعديل العنوان لهذا الطلب. القسم موجود في المسار الفيزيائي والديجيتال، ويُحفظ `branch_name` و`delivery_address` عند إدراج الطلب نفسه؛ لا يُستخدم UPDATE يتجاوز حارس حقول الطبيب. التحقق على الخادم يمنع استعمال فرع حساب آخر، ويحافظ على مسار Pending Review وقيم الإدراج المحاسبية السابقة.

القائمة الفارغة في screenshot كانت نتيجة أن **services في قاعدة العرض المحلية بها صفر سجلات**. أُضيفت ثلاثة خدمات موسومة «تجربة محلية» وثلاث أسعار تجريبية للعرض فقط، مع فرعين للطبيب التجريبي. لم تُنسخ أسعار الإنتاج ولم تُعدّل بياناته. تم أيضًا إصلاح تحميل العنوان بصورة مستقلة عن فشل تصنيفات الخدمات، وعرض الخدمات ذات التصنيف المفقود، وإظهار خطأ التحميل/القائمة الفارغة بدل نموذج غير قابل للاستخدام. تتوحد قراءة أرقام الأسنان بالفاصلة العربية أو الإنجليزية والمسافات.

التحقق بعد هذا التحديث: **14 اختبار متصفح** على الكمبيوتر والموبايل، تشمل تسجيل مركز فعلي مع طبيب وفرع، تعبئة العنوان الرئيسي، اختيار الفرع، استمرار عنوان الشحن في الديجيتال وظهور الخدمات؛ **49 اختبار SQL** تشمل الهاتف والصلاحيات والتسجيل والكود والفروع وحفظ عنوان الطلب ومنع الفرع الأجنبي؛ **288 اختبار وحدة** ناجحة، والبناء وlint للملفات المتأثرة ناجحان. بعض اختبارات أمان المشروع أضيفت بالتوازي خارج هذه المهمة، لذا زيادة العدد الكلي لا تخص هذا التغيير وحده.

الملفات الجديدة: `20261007010000_doctor_onboarding_and_order_destination.sql`، و`doctor_onboarding_and_destination.test.sql`، و`NewDoctorRegistration.tsx`. يجب تطبيق الترحيل الجديد في بيئة الاختبار/التشغيل قبل إصدار الواجهة المتغيرة؛ طُبق هنا على مشروع العرض المحلي وحده. السكربت المحلي يزرع الخدمات والفروع التجريبية لإعادة التجربة.

1. **قبل إتاحة دخول الهاتف للإنتاج:** تنفيذ endpoint خادم لإصدار وإرسال وتحقق OTP، حفظ أسرار Meta/HMAC على الخادم، عدم إرجاع OTP للعميل، تأكيد نتيجة الإرسال وإبطال التحدي عند فشله، حد الهاتف وIP الموثوق، انتهاء خمس دقائق وثلاث محاولات وSMS fallback. استبدال إنشاء/تدوير كلمات المرور المباشر في SQL بمسار Supabase Auth إداري مناسب على الخادم. لا تفعّل علم mock على الإنتاج.
2. **بوابة القبول للمصادقة:** تشغيل سلسلة ترحيلات المشروع في بيئة staging مستقلة، اختبارات grants/RLS الكاملة، اختبار دخول جديد ومتكرر وحساب موقوف ومطابقة `phone2` وطلب مرفوض واعتماد رقم جديد ومركز. اختبار UI للتحقق وإعادة الإرسال وطلب الكود والاعتماد. التحقق من تطابق الأرصدة بمقارنة قراءة فقط عند التجهيز للإطلاق.
3. **المراكز:** بناء مبدل الفروع وRPC/RLS للقراءة وإنشاء الطلبات على النطاق المصرح، واختبارات منع التسرب بين مركزين. الاعتماد الحالي على كيان مركز لا يحقق بمفرده قراءة جميع أبنائه.
4. **الاستلام والشحن:** حقول طلب استلام واضحة، حالة تنسيق قابلة للتتبع، وإشعار المنسق؛ رفع STL/PLY محمي. اربط خطوة الشحن بحالة الشحنة الفعلية بدل جاهزية الإنتاج.
5. **التتبع والتقييم:** ربط شريط المراحل بمسار الإنتاج الحالي والداخلي، ETA من محرك السعة، واختبارات حفظ النجوم والوسوم والملاحظات على `final_delivered`.
6. **الماليات:** مراجعة قراءة كشف الطبيب وتطابقه مع المحرك المركزي قبل اعتماد تصميم الرصيد الجديد، ثم PDF والضمان. حساب الرصيد الموجود بالصفحة لم يُستبدل خلال هذه المراجعة، ولم يُثبت تطابقه المحاسبي. كذلك الرصيد الصافي وحده لا يثبت عدم وجود متأخرات.
7. **الإعدادات والموبايل:** ضبط رقم واتساب المعمل الحقيقي؛ يوجد رقم placeholder `201000000000` في روابط البوابة الحالية. ثم اختبار responsive وCapacitor وFCM والبصمة وبناء المنصتين.

للاختبار المحلي فقط، يتطلب المسار إعداد `VITE_OTP_CHANNEL=mock` في Vite development، وعلى قاعدة اختبار مستقلة علم `app.doctor_otp_mock_enabled=on` ومفتاح `app.doctor_otp_hmac_key` خاص بها. الاختبارات تضبطهما داخل المعاملة وتعيدها بـ rollback. لا تضع مفتاح HMAC أو أسرار Meta في متغيرات `VITE_*`.
